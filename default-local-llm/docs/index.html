Default Local LLM Documentation

Purpose and interface

Default Local LLM gives Ploinky an OpenAI-compatible local Chat Completions endpoint backed by a small model bundled into its container image. It starts llama-server on loopback and exposes it through the shared AgentServer, so consumers use the Ploinky agent endpoint without connecting directly to the inference process.

The manifest declares one endpoints.chatCompletions command and marks streaming as supported. The agent does not expose model discovery, embeddings, tools, or a separate public llama.cpp port.

Chat Completions requests

AgentServer invokes chat-completions.mjs with a JSON envelope containing endpoint, request, and metadata. The Chat Completions handler requires request.messages to be an array and forwards the complete request object to http://127.0.0.1:${LLAMA_SERVER_PORT}/v1/chat/completions. This preserves model parameters accepted by llama-server in addition to the required messages.

{
  "request": {
    "messages": [
      { "role": "user", "content": "Explain this function." }
    ]
  }
}

For a non-streaming request, the handler requires an upstream 2xx response, parses the JSON body, and writes that response to standard output. AgentServer returns it through the OpenAI-compatible endpoint.

Streaming

When request.stream is true, the handler asks llama-server for the same streaming request and copies every upstream response chunk directly to standard output. AgentServer forwards the Server-Sent Events stream. The handler does not buffer, reinterpret, or synthesize stream events.

Startup and readiness

startup.sh first verifies that the configured model artifact exists. It launches llama-server on 127.0.0.1, waits up to 120 one-second attempts for /health, and exits with diagnostic log output if the process terminates before becoming ready. AgentServer starts only after the local health endpoint succeeds.

The manifest's readiness probe calls the same loopback /health endpoint every five seconds with a ten-second timeout. Its failure threshold allows llama-server to initialize before Ploinky marks the agent unavailable.

Runtime configuration

VariableDefault and effect
LLAMA_MODEL_PATH/opt/models/Qwen2.5-Coder-1.5B-Instruct-Q4_K_M.gguf; selects the required GGUF file.
LLAMA_SERVER_PORT8080; selects the loopback inference and health port.
LLAMA_SERVER_BINllama-server; selects the executable.
LLAMA_CTX_SIZE4096; supplies --ctx-size.
LLAMA_THREADS2; supplies --threads for generation. Unset or empty values use this default.
LLAMA_THREADS_BATCHInherits the effective LLAMA_THREADS when unset or empty; supplies --threads-batch for prompt processing.
LLAMA_LOG/tmp/llama-server.log; stores startup and inference-process logs.
PLOINKY_AGENT_LIB_DIR/Agent; locates server/AgentServer.sh.

Thread settings must be decimal integers from 1 through 2147483647, without leading zeroes. Invalid values fail before either service starts. The conservative two-thread default reduces inference competition with other workspace services; operators can tune generation and prompt processing independently through the agent profile. These settings limit inference parallelism, not total process CPU usage: they do not reserve cores or provide a cgroup CPU quota. A strict quota requires a runtime with independently enforced agent cgroups.

Failure behavior and limits

Malformed handler input writes a concise error to standard error and exits with status 2. An upstream non-2xx response, missing streaming body, connection failure, or invalid non-streaming JSON writes an upstream failure message and exits with status 1; AgentServer converts a non-zero handler exit into a server error. The non-streaming helper includes at most the first 200 characters of the upstream error body.

The runtime serves one baked Qwen2.5-Coder-1.5B-Instruct Q4_K_M model by default. Performance, context capacity, and output quality are constrained by the selected model, context size, CPU resources, and llama.cpp behavior. The proxy does not add retries, request queues, model fallback, response normalization, or authentication of its own beyond the surrounding Ploinky service.
